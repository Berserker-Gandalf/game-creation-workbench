## 4. 下一步顺序与验收条件

### 第一阶段：收口一条真实创作链（P0）

选定一条最小链路，例如“设计资料 → SUNO或Tripo方案 → 明确的收费授权 → 一次真实生成 → 查询 → 保存可核对结果”。一次只验证一个供应商、区域和模型，保留成功/失败和积分证据；结果未知先查账，不自动重提。API 文本与 Unity/GitHub 各按上表补独立验收。

**通过条件：**有对应账户的成功记录、模型/编号/时间、产出校验及费用记录；未授权/撤销/超时分支可复现；模拟与真实证据分开。未覆盖的供应商继续保留实验标识。

### 第二阶段：作业与交付闭环（P1，0.12基础已交付）

以下1–3及4中的SUNO接入已在0.12以模拟服务/自制音频验证；工程重绑定和大资料包本地恢复仍未完成。后续增加事件订阅和并发调度前先测量规模。

1. 统一动作结果为可区分的运行中、成功、失败、未知、需用户处理；保留供应商原状态和父子执行关联。
2. 增加作业列表、手动接续和受支持的停止入口；服务重启只恢复查询/核对，收费提交不自动重放。
3. 关联任务、资产版本、生成参数及验收证据；设计或资产变化后触发复核。
4. 为 SUNO 加受限音频下载/校验/登记，为工程增加安全重绑定和大资料包本地恢复入口。

**通过条件：**可从任务定位确切产出和哈希；中断/重启可继续查询同一任务；旧结果不冒充新交付，外部失败不假装回滚；下载与恢复不越界、不覆盖原工程。

### 桌面封装轨道：先完成基础再分发（P1）

仍建议先验证 Windows x64，复用 React/FastAPI 和私有真实 Python；Tauri/Electron 的取舍与源码依据见 [应用评估](PROGRESS_AND_APP_READINESS_2026-10-26.md)。资源目录与用户数据分离、MCP 解释器语义、后台/端口/实例归属、首次依赖诊断和迁移前备份是首包门槛。

**通过条件：**无开发工具的干净机器可离线使用核心项目管理；中文/空格路径和不可写安装目录可用；更新失败可恢复；卸载默认保留数据；可选工具缺失不阻断核心；安装器包内工具与浏览器源码模式的权限核验一致。

自动更新可晚于首个内测包；启用时再加入签名校验与回退，不先制造一个无法保留数据的“外壳版”。

### 第三阶段：规模和自主协作（P2）

先用 1,000 资产/300 文档夹具测量首屏、检索、刷新和内存，再优化增量事件/分页、按需上下文和出处索引；不直接把所有历史与动作结果塞进提示。可选软预算和多 Agent 分派分别定义合约后再开发。

**通过条件：**基准结果可复现，刷新不漏状态，长历史决策有出处，超限有明确处理；有并行调度时具备资源锁、权限继承规则、冲突检查和非自动验收边界。
